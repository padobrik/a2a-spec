# Spec format

A spec is a YAML file in the specs directory (`handshake/specs/` by default).
It describes what one consumer agent needs from one producer agent's output.
Every key sits under `spec:`. An unknown key is an error that names the key.
A key removed in 0.9 (`semantic`, `statistical`) is an error that says what to
use instead.

`handshake infer` writes most of a spec from the consumer's code. You can also
write one by hand, or edit an inferred one. For how to write the rules, see
[Writing specs](writing-specs.md).

## Example

This spec is what `handshake infer` writes for `examples/helpers_and_lists`:

```yaml
# Generated by 'handshake infer' from agents/writer.py:writer_agent and 2 planner-agent snapshot(s). Review before committing.
#   headers: required, read at line 5, 6
#   ...
spec:
  name: planner-agent-to-writer-agent
  version: '1.0'
  producer: planner-agent
  consumer: writer-agent
  description: Fields writer-agent reads from planner-agent (inferred)
  inferred_from: agents/writer.py:writer_agent
  read_at:
    headers: [5, 6]
    headers.title: [6]
    title: [6]
    searches: [7, 12]
    searches[].query: [12]
    searches[].reason: [12]
  structural:
    type: object
    required: [headers, title, searches]
    properties:
      headers:
        type: object
        required: [title]
        properties:
          title: {type: string}
      title: {type: string}
      searches:
        type: array
        items:
          type: object
          required: [query, reason]
          properties:
            query: {type: string}
            reason: {type: string}
```

## Keys

| Key | Required | Written by `infer` | Meaning |
|---|---|---|---|
| `name` | yes | yes | The spec's name, used in reports and by the `handshake_check` pytest fixture. `infer` uses `<producer>-to-<consumer>` unless `--name` is given. |
| `version` | yes | yes (`'1.0'`) | Your version of this contract. agent-handshake does not read it. |
| `producer` | yes | yes | The agent id whose output the spec checks. Snapshots are matched by this id. |
| `consumer` | yes | yes | The agent id that reads the output. Used in messages, for example by `diff`. |
| `description` | no | yes | Free text. |
| `inferred_from` | no | yes | The consumer function, as `path/to/file.py:function` (POSIX separators, relative to where `infer` ran). `infer --check` reads this function again and fails when the spec is out of date. Specs without it are not checked by `infer --check`. |
| `read_at` | no | yes | For each field path, the lines where the consumer reads it. `diff` uses it to say where a removed or retyped field is read: `resolution-agent reads it at agents/resolution.py:4`. |
| `reads_unknown_keys` | no | when `true` | `true` when the consumer also reads keys that `infer` cannot name, for example `data[key]`, or gives the input to a function it does not follow. `diff` then keeps the normal rating of a change to a field the spec does not name, instead of `INFO`. `infer --check` fails if the code reads such keys but the spec does not set it. |
| `allow_missing` | no | with `--allow-missing` | Field paths the consumer reads that the producer leaves out on purpose. `infer` makes them optional instead of failing. `infer --check` accepts a `data["key"]` read of them, and its "Regenerate" command repeats `--allow-missing` for each. |
| `structural` | yes | yes | A JSON Schema (Draft 7) object for the output. See below. |
| `policy` | no | no | Rules on the content of the output: `regex` and `custom`. See [Writing specs](writing-specs.md). |

## Field paths

`read_at` and `allow_missing` name fields by path:

- `category`: a top-level field;
- `customer.tier`: a field of a nested object;
- `searches[].query`: the field `query` of each item of the list `searches`.

`infer` writes the parent of each nested field too (`customer` for
`customer.tier`), because reading the child needs the parent.

## `structural`

`structural` is a JSON Schema object with `type`, `required` and `properties`.
You can use any Draft 7 keyword inside `properties` (`enum`, `minLength`,
`minimum`, `pattern` and others).

`infer` writes:

- `required` for a field the consumer reads with `data["key"]` (or an attribute
  of a typed object), or a field the producer sent in every snapshot. A field
  read with a default and sometimes missing in the snapshots is optional.
- `type` from the values in the snapshots. Mixed values give a list, such as
  `["string", "null"]`.
- A nested object as `type: object` with its own `required` and `properties`.
- A list whose items the consumer reads as `type: array` with an `items` schema
  for one item. Every item is checked. If the producer drops `query` from one
  search, the scenario fails with `'query' is a required property`.

Fields the consumer does not read are left out. The producer can change them
freely: `diff` rates such a change as `INFO`.

For an agent that returns plain text, use `structural: {type: string}` and
check the text with `regex` rules. A spec that expects an object fails on a
text snapshot with "the output is text, but the spec expects an object".

## Comments

`infer` writes a comment header before `spec:`: where the spec came from, and
one line per field with its status and lines. The header is for review only.
agent-handshake ignores comments, so you can edit or remove it.
